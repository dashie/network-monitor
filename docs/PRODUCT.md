# Product — uptime-monitor

## Purpose and vision

Give an operator a tool that answers "which link or which peer is broken right now" with a record of exactly when it broke and when it recovered, using a few kilobytes of storage and no infrastructure.

`uptime-monitor` replaces the ping loop, the scattered shell history, and the heavyweight uptime platform with one binary that fits on a NAS, in a container, and in a cron-free long-running process.

## Users

- **Homelab and NAS owner.** Runs QNAP, a small server, or a Raspberry Pi with several uplinks and wants to know when a WAN link, a VPN tunnel, or a peer stops answering — without deploying a monitoring stack.
- **System or network administrator.** Needs to verify that reachability is identical from a specific interface (`eth1`, `wg0`, `pppoe0`) and not merely from the default route.
- **On-call engineer.** Asks "since when is $host down, and did it flap?" and needs an exact timestamped history that survives restarts.
- **Edge or embedded operator.** Deploys on a device where only a single static binary can be shipped and where database servers are impossible.
- **Automation author.** Consumes the SQLite database or the JSON output of the query command from scripts and dashboards.

## Problem and value proposition

Checking whether a host is reachable is trivial — `ping 1.1.1.1` — but keeping a reliable record of *when* reachability changed is not.

Today this is handled with a ping loop that logs every reply (megabytes of log for one day), with an uptime platform that must be hosted and maintained, or with ad-hoc manual checks that leave no history at all. A ping loop also loses the essential piece of information in a multi-homed host: *which interface* the probe left from. `ping` can bind the source address or device (`ping -I eth1 1.1.1.1`), but the standard monitoring tools cannot, and the result depends on the routing table of the moment rather than on the configured intent.

The consequence is a history that is either too large, absent, or not attributable to an interface.

`uptime-monitor` records transitions instead of samples: one row when a target goes down, one when it comes back, timestamped in UTC. Storage is proportional to incidents, queries are instant, and the database can be read while monitoring continues.

Probes are bound to the configured interface with the semantics of `ping -I`, the whole configuration is overridable from the command line, and the entire tool is a single executable with no runtime dependency — on a laptop, in Docker, or on a QNAP.

## Scope

### In scope

- A TOML configuration file with global defaults (`interval_ms`, `timeout_ms`, `database`, `retention_days`) and a list of targets (`ip`, optional `interface`, optional `label`).
- Optional notification channels — Telegram, a webhook, and a log file — declared once and
  enabled by name, globally or per target, that tell the operator when a target changes state
  and when the monitor starts, with one message per incident and a stabilised recovery.
- A command-line parameter for every configuration option, with the precedence `command line > configuration file > built-in default`.
- ICMP echo probing of IPv4 targets, one echo request per target per interval, with an explicit timeout.
- Binding a probe to a named network interface on macOS, Linux, and Windows, with the semantics of `ping -I <interface> <address>`; the default-route interface is used when no interface is configured.
- Persistence of state transitions only, in an embedded SQLite database created and migrated by the binary itself.
- Concurrent reads: the `query` subcommand reads the event history and the current state while monitoring runs.
- Configurable retention of events older than `retention_days`.
- A single statically linked executable per platform (macOS, Linux, Windows) and a container image for Linux deployments, including QNAP Container Station.
- A simulated mode that serves the same page, API and export over a deterministic generated history, for development, demonstration and review, with no probe and no database.
- Line-based logging on stderr and meaningful exit codes for scripting.
- Deployment of a changed configuration: a dry run (`check`), an opt-in candidate that is promoted only after every target has probed once (`--try`), and one active snapshot of the last configuration that started (`<main>.active`).
- A one-shot `init` that scaffolds a minimal, runnable setup in a new folder.
- A `manual` subcommand that prints the embedded user guide as Markdown, with `man` as an alias.

### Out of scope

- Any programmatic write API: the JSON API of `FR-26` reads the history and never changes it; the `import` command remains the only way to load events from outside.
- A configuration UI: the configuration stays a TOML file on the server plus the command-line flags (`FR-1`, `FR-2`, `BR-3`), so it can be read, reviewed, versioned and restored from a backup with the rest of the machine. The page offers no settings screen, and no remote surface can add a target, change an interval or alter what is probed.
- Notification transports other than the three built-in channels (mail, MQTT, Slack-specific payloads, a command hook): the database stays the integration point for everything else.
- Metrics export (Prometheus, OpenTelemetry) and dashboards.
- Probe types other than ICMP echo: no TCP, UDP, HTTP, DNS, or traceroute probes.
- IPv6 targets: the first milestone probes IPv4 only; ICMPv6 is tracked as a follow-up.
- High availability, clustering, and replication of the database.
- OS-level service installation or scheduling, including a Windows service or a macOS launchd job: the binary is shipped and the supervisor is the operator's choice; `init` writes only inside a folder and installs no systemd unit, launchd job, or Windows service.

## Functional behaviour

Each requirement is observable and independently verifiable. Implementation details
belong in [ARCHITECTURE.md](./ARCHITECTURE.md).

- `FR-1`: The tool reads a TOML configuration file. `--config <path>` must exist and parse; without the option, `./uptime-monitor.toml` is read when present and skipped otherwise, so a fully command-line invocation needs no file. A malformed file, or an explicit path that does not exist, is a startup error reported on stderr with a non-zero exit code.
- `FR-2`: Every configuration option can be given on the command line and overrides the file; targets are supplied with the repeatable `--target [method:]address[,key=value]…` option — `1.1.1.1`, `tcp:1.1.1.1:443`, `dns:example.com@9.9.9.9`, `http:https://example.com/health` — where a bare address means `icmp` and the keys `interface`, `label`, `timeout_ms`, `interval_ms`, `record`, and `expect` follow the method. The flag replaces the target list of the file when present. The `listen` key of `FR-35` has `monitor --listen` as its flag. The `[[notification]]` declarations and the `notify` lists of `FR-25` are the deliberate exception: they carry secrets, so they are read from the file only.
- `FR-3`: The tool runs one probe of the target's method per configured interval and classifies the result as reachable or unreachable. For an `icmp` target the probe is one echo request: reachable means a matching reply arrived within `timeout_ms`. The interval is the pause after a probe, so a target answers every `rtt + interval` and a silent one every `timeout_ms + interval`; `timeout_ms` bounds the whole probe whatever other traffic the machine carries. An interval shorter than the timeout is accepted: it just means a silent target is probed less often than an answering one. `interval_ms` and `timeout_ms` may be given per target and override the global values.
- `FR-4`: When an `icmp` or `tcp` target has an interface configured, the probe leaves through that interface with the semantics of `ping -I <interface> <address>`; when it has none, the default-route interface of the operating system is used. The interface is given by name on Linux and macOS (`eth1`, `en0`) and by numeric interface index on Windows. A `dns` or `http` target that names one is refused as invalid configuration: neither method can bind its transport to a device here.
- `FR-5`: A state transition is recorded only when the verdict of a probe cycle differs from the last recorded verdict of that target. Repeated verdicts produce no database write.
- `FR-6`: The first probe cycle of a target always records a transition, from `unknown` to the observed `up` or `down`.
- `FR-7`: The tool stores events in an embedded SQLite database, creating the file, the schema, and the migration metadata when they are absent.
- `FR-8`: The event history and the current state of every target can be read while the monitor is running, without stopping or pausing it.
- `FR-9`: The `query` subcommand reports the current state per target and the event history filtered by target and time range, in a human-readable table and in JSON selected by `--format json`.
- `FR-10`: When `retention_days` is greater than zero, events older than that window are deleted periodically; `0` keeps every event.
- `FR-11`: `SIGINT` and `SIGTERM` stop the monitor cleanly within one probe cycle, with no partially written event.
- `FR-12`: `--show-config` prints the effective configuration, after defaults, file, and command line have been merged, and exits without probing. A path that came from the file is printed as the absolute path the process resolved (BR-11), and the merged `listen` address is printed when one is set.
- `FR-13`: Invalid configuration — an unknown option, a non-positive interval or timeout, an unparseable or IPv6 address, a target listed twice, a configured interface that does not exist, an unknown method, a key that does not belong to the method of its target, a missing key the method requires, a port of zero, an unparseable URL or record type, `interface` on a `dns` or `http` target, or a `monitor` run without targets — aborts startup with a message naming the offending key and a non-zero exit code. The `check` subcommand (`FR-30`) reports the same conditions before a start, so a configuration that would abort startup is named there first.
- `FR-14`: The tool runs as a single executable with no runtime dependency, and as a container image that needs only the `NET_RAW` capability for ICMP targets. HTTPS verification uses certificate roots compiled into the binary, so a host with an unusual trust store still works and a TLS-inspecting proxy requires a rebuild.
- `FR-15`: Every probe cycle and every transition is observable on stderr according to `--log-level` (`error`, `warn`, `info`, `debug`), in a stable line-based format `<RFC 3339> <LEVEL> <logger> [<target>] <message>`, where the logger is `monitor` for the process and `notification` for a channel. A `monitor` or `serve` start states at `info` that the process initializes, the configuration file it read or that it read none, one line per declared notification channel, one line for the root `notify` list or that it enables none, one line per target key it initialized, and — when the page is served — that the page is ready together with the address it listens on.

- `FR-16`: While monitoring runs, the tool re-reads the configuration file within one second of a change and applies the new interval, timeout, target list, and retention without a restart, writing one `INFO` line that states the configuration was updated. A file that cannot be read, does not parse, or leaves no targets is rejected with a warning and the previous configuration stays in effect. A changed `database` path or `listen` address is reported and used only from the next start.

- `FR-17`: The read-only web page over the event database is available in two ways from the same binary: `serve --listen …` publishes it without probing, and `monitor` with a listen address — its `--listen` flag or the file's `listen` key (`FR-35`) — publishes it from the monitoring process, so one command both records and shows the history. The page shows one lane per target with green, red, and grey bands for `up`, `down`, and `unknown`; a lane is one bar, rounded only at its two outer ends, so the bands of the states meet square and the breaks between them stay readable. A fault too short to reach a visible width is drawn at a minimum width, centred on the time it covered, and coloured orange instead of red, so a brief outage is seen while its width is never read as its duration. The window is the last hour by default and the links select the last 1, 2, 4, 6, 12, or 24 hours, narrowest first, so `/?window=24h` is a bookmarkable state. The lanes follow the `priority` a target states in the configuration — lowest number first, the targets without one after them, by key, with the key breaking a tie —, and the same order is the one the JSON API lists, so a board reads in the order its operator chose. Every page opens with the identity block of the application — the mark, the name, and the tagline — as a link to `/`, the API reference included, so a selection anywhere inside that block returns to the timeline. The page reads the database and never writes to it: a database written by an older version is read without the cause columns it lacks, and the first `monitor` or `import` adds them and converts the target keys of a history written before methods existed. It has no client-side interaction beyond following a link, opening the cause of a fault, and asking for the refresh a held countdown withholds: the browser reloads it every 30 s, and that countdown is held while a cause is open — a banner across the top of the page states the hold and offers `Refresh now` — so a message being read is never taken away by the reload, and a browser without the script falls back to a `noscript` reload of the same interval. Every instant is written in UTC and formatted by the browser with the locale and the time zone of the reader; without the script the page shows the same instants in UTC, labelled as such. Each lane states, from left to right, the faults of the window it shows, the average `up` run with its spread, the longest `up` run of the window, and how long the target has been `up` without a drop, so the same row answers "how bad was it", "how long does it stay up", and "is it up right now, and since when". Below the chart the last 10 faults of any target are listed in a table that starts under its own heading, separated from the chart above by a rule at the top of its header row, which stays in place while a long table scrolls — except in the stacked layout under 700 px, where the header is two lines tall and travels with the table. A row states, in the first column, the name its lane uses — the label with the key in smaller type under it, or the key alone when the target has no label — then its start, the code of the fault, and its duration — an ongoing one included — in the last column. The four columns start from a stated share of the width — 15, 30, 45 and 10 per cent — so a long name does not squeeze the date and a short code does not leave a gap, and every row is the same height, so the table reads as a grid. A share is where a column starts, not a limit on what it may hold: the name of a target, its key, the code of a cause, the date and the time of an instant and the average `up` run with its spread are each one unbreakable token, an instant may fall on two lines with the date above the time and never inside either half, and a column that cannot hold its token widens the table, which scrolls sideways under its own header instead of breaking the text. Under the width where four columns stop fitting — 700 px — a row states its values in two columns of two lines instead of losing them: the fault table puts the target with its instant under it in the first column and the cause with its duration under it in the second, and the header row takes the same mapping, so every label stays above the value it names and the cells keep their roles, the table still being a table for a screen reader. An ongoing fault states how long it has lasted and, under it in smaller type, "and counting" — beside it on the same line in the stacked layout under 700 px. Selecting a fault opens the standard message of its cause in a row of its own underneath, and closes any other; the two are drawn as one block — one surface, one bar down their left, no rule between them while the message is open, the message indented inside that bar and padded on every side — so the message reads as part of that row and never as a fault of its own, and the code of the cause opens it as well as the rest of the row; a browser without JavaScript shows the same message on hover. A row written before causes existed states an empty cell and opens nothing. The per-day buckets of the detail page are UTC days by `BR-6`, so their dates are localised in format but keep the UTC day they belong to. Selecting a lane opens a page for that target: its toolbar states the page on one line — `targets`, the way back to the timeline, a link to `/` and never a step into the browser history, then the label with the address in parentheses in bold, the parts separated by a dot —, the totals of the period sit under it, opened by the current state of the target and how long it has held — white on a tile of the colour the chart gives that state, the only widget drawn that way —, then the faults, the down time, and the average `up` run of the period — the four always in that order, standing four across while the window holds them, then two and two, and under the narrowest window with the state alone above the other three —, and a selector offers the last 30, 60, 90, 180, or 360 days — shortest first, 30 days when the query names none — with the choice carried in the URL (`/target?target=…&days=90d`) so it survives the 30 s reload and can be bookmarked. Between the bars and the table the page lists the last 10 faults of that target, with the same names and the same columns as the timeline page. One bar per day follows for the chosen period, with the count above every day while the columns have room for it, a quiet day stating a muted zero at the baseline so a measured nothing is not read as missing data; past about seven weeks the counts are omitted and the table carries the exact numbers. Under the chart, and before the day-by-day table, the last 10 faults of that target are listed in the same table the timeline draws, columns and `Download History` link included. A table with one row per day states the number of faults, the total down time, and the average `up` run of that day, with the longest run of the same window under the mean; the mean and its spread are one unbreakable figure and the day is a date that never breaks. Under the same 700 px it states the day with its fault count beside it on the first line, and the down time with the average `up` run on the second, its header mapped the same way. The first row is the current UTC day, which is still running, so its average `up` run covers the last 24 hours instead, tagged `last 24 h` and styled apart from the figures of a complete day; both pages label that figure `AVG UP`. The header of that page states the faults, the down time, and the average `up` run of the whole period with the longest run of it. Both pages close with a short manual in the footer — the meaning of a lane and of a bar, the 30 s reload, the local time zone, how the window changes, and where the history is downloaded — so nothing explains itself above the chart. Both pages are gzipped when the request advertises gzip and `--compression` is left at `auto`, and sent as they are otherwise, so a deployment behind a compressing proxy states `off`; `Vary: Accept-Encoding` keeps a cache from answering with the wrong form, and the CSV archive is never compressed twice. Every request opens the database read-only and answers `503` with the reason when it is missing. The page has no authentication. The server stops with the process that runs it, on `SIGINT` or `SIGTERM`.

- `FR-18`: The page offers a download of the whole history, as a gzip-compressed CSV file (`/export/faults.csv.gz`, named `faults-YYYYMMDD.csv.gz`; the path `/export/disconnections.csv.gz` of an earlier version answers `308` towards it). The same link on a target page downloads the history of that target only (`/export/faults.csv.gz?target=…`) and names the file after it — `faults-<target>-YYYYMMDD.csv.gz`, the name the page shows, its key when it has no label — so the file states whose history it holds and two downloads never collide. The CSV has one row per event with the target, its label, its interface, the state reached (`up` or `down`), the instant, the round-trip time when the event is a return to `up`, and the code and the message of the cause when the event is a fault. The `target` value is the canonical key of the target (`icmp://1.1.1.1`, `tcp://1.1.1.1:443`, `dns://example.com@9.9.9.9`, `https://example.com/health`). The columns are the ones the import reads, so an exported file can be imported back as it is. The file is compressed while it is sent: the server reads the history in pages and never builds the file in memory.

- `FR-19`: The `import` subcommand restores a history from the file the page offers for download, so a redeployed service does not lose its record. The source is a file path, an `http://` URL, or `-` for standard input. The format is recognised from the content — a gzipped or a plain CSV — with no flag, and it is the format `FR-18` writes: one row per event, replayed as it is, labels and interfaces included. An archive written before causes existed ends after its round-trip column: it imports unchanged, and its rows carry no cause. A file in the older no-cause format of an earlier version is refused with a message asking for a fresh export. Importing the same file twice changes nothing: an event already present is skipped and counted. Rows that are not part of the format are skipped and counted, and the command reports how many events it wrote, for how many targets, how many rows it ignored, and how many events it dropped as repeats. The rows may arrive in any order: the state each event replaced, and the removal of an event that repeats the state before it, are worked out from the timestamps, not from the order of the lines. The command only reads the archive and only writes the database; it probes nothing and serves nothing. `https` is refused with an explanation: the import path speaks plain HTTP only. With `--replace-window` the import replaces instead of merging: for every target the archive mentions, the events between that target's earliest and latest instant in the archive are deleted before the archive is written, and that target's events before and after its own window are kept, so a corrected archive can be re-applied to the same database; a target the archive does not mention keeps all of its events. An archive with no row has no window: the command fails and deletes nothing.
- `FR-20`: A `tcp` target names a host and a port. The probe opens one TCP connection and closes it without sending anything: the handshake completing is `up`, a refusal, a reset, or the timeout expiring is `down`. A peer that closes the connection immediately after accepting it is still `up`: the handshake completed, so something is listening. A host name is resolved first; a name that does not resolve, or a socket the host cannot open, is a local failure and never a state change. The cause of the verdict is stated as `TCP.REFUSED`, `TCP.RESET`, or `TCP.TIMEOUT`; a local failure carries a code of its own (`TCP.RESOLVE`, `TCP.SOCKET`, `TCP.CONNECT`, `TCP.INTERFACE`).
- `FR-21`: A `dns` target names a record to resolve and, optionally, the server to ask. With a server, the tool sends one UDP question and reads the answer: a record of the requested type is `up`, `NXDOMAIN` or an answer with no such record is `down`, and `SERVFAIL`, `REFUSED`, `NOTIMP`, a truncated answer, or an unusable answer is a local failure. Without a server the system resolver is asked, which also consults the local hosts file; a name this host cannot resolve is `down`, because the platform offers no portable way to tell a missing name from an unreachable resolver. The cause of the verdict is stated as `DNS.NXDOMAIN`, `DNS.NO_RECORD`, `DNS.TIMEOUT`, or `DNS.UNRESOLVED`; a local failure carries `DNS.BUILD`, `DNS.SOCKET`, `DNS.SERVER_FAILURE`, or `DNS.UNUSABLE`.
- `FR-22`: An `http` target names a URL (`http://` or `https://`). The probe sends one `GET` — no redirect, no body, no authentication — and reads the status line: a status inside the expectation is `up`, a status outside it is `down`, and a refusal, a timeout, or a TLS failure is `down`. The expectation defaults to `200`–`399` and accepts classes (`2xx`) and exact codes; a malformed answer or a head larger than 8 KiB is a local failure. HTTPS verifies the certificate chain against the embedded roots and cannot be told to skip verification. The cause of the verdict is stated as `HTTP.UNEXPECTED_STATUS` with the status and the expectation, `HTTP.TLS` for a handshake that failed, or one of the connection codes of `TCP`; a local failure carries `HTTP.RESOLVE`, `HTTP.TLS_INIT`, `HTTP.MALFORMED`, or `HTTP.HEAD_LIMIT`.
- `FR-23`: The identity of a target is its canonical key: the method scheme plus what identifies the endpoint. It is what the database stores, what the page links to, and what `query` filters on. A history written before methods existed keeps its events: the first writable open rewrites each bare address to its `icmp://` key once, and the import reads either form.
- `FR-24`: Every failure of a probe cycle states a code and a standard message. The code is a short uppercase token prefixed with the layer that reported the failure — `ICMP`, `TCP`, `DNS`, `HTTP`, or `PROBE` — so a log line and a table row can be filtered by it. The message is one sentence declared once in the code as a template, with the details of the occurrence inserted: the host and port, the name and the server asked, the status and the expectation, the timeout, or the text the platform returned. A detail the code did not supply reads `unknown`, so a reader never sees a placeholder. Both halves are English and neither is translated. Only a verdict is persisted; a local failure carries the same pair in the log and never becomes a state change (`BR-4`).
- `FR-25`: Notification channels are declared once in a `[[notification]]` array and enabled by name. Each entry states a unique `name`, a `type` (`telegram`, `webhook` or `logfile`), and `stabilize_seconds` (default `60`, `0` reports at once); a channel has no scope of its own. The root `notify` list enables channels for global events and for every target that does not override it; a target's `notify` list replaces it for that target, an absent key inherits, and `notify = []` silences the target. A recorded transition to `down` is reported at once, with the target, the instant, and the code and message of the cause. A transition to `up` is reported only after `up` has held continuously for `stabilize_seconds`; a transition back to `down` inside that window reports nothing. After an `up` message the next `down` is a new message, while a `down` that repeats an already-notified `down` is silent. The first verdict of a target after a start or a restart is reported under the same rules. Every channel the root list enables also receives one `READY` message when the monitor is ready and every target is being probed (the configuration file, the target keys, and the page address), one `CONFIG` message per applied or rejected reload, and one `STOPPED` message, attempted once, when the monitor stops; every declared channel states `CHANNEL` on itself when it starts. A message is one typed fact — global or target scope, the event, the target key and label, the state, the cause, and the instant — which each channel renders as it needs. A failed delivery is attempted five times, waiting 1, 2, 4, and 8 seconds, then dropped with one `WARN` line; one channel never delays a probe or another channel, and a notification never changes what is recorded. The declarations and the lists are read from the file only (the exception of `FR-2`), every secret is printed as `<redacted>` by `--show-config`, and no secret or URL path appears in a log line or an error message. A channel that cannot open, an unknown name, a duplicate name, and two channels on one destination are configuration errors that stop the process before the first probe; a declared channel that nothing enables is legal, is reported as one `WARN` line, and receives nothing. A `[telegram]` section is accepted as a legacy alias for one release: it declares a channel named `telegram` and enables it globally.
- `FR-26`: The read-only page is accompanied by a read-only JSON API under `/api/v1`, served on the same socket and with the same absence of authentication (`BR-8`). `GET /api/v1/targets` states every target — its key, label, interface, state, when that state began, when it was first seen, its last round-trip time, and how long it has been `up` — ordered by key; `GET /api/v1/faults` states the faults newest first, each with its id, target, label, interface, start, cause, end, duration, and whether it is still open; `GET /api/v1/faults/daily` states, per UTC day oldest first, the target it belongs to or `null` when the answer aggregates every target, the faults, the down time, the mean and the longest `up` run, and whether the day is still running, its window being the last 30 days when the request names no `from`, and only the days of the returned page being read, so the cost of a request follows `limit` and not the length of the window; `GET /api/v1/openapi.json` serves the OpenAPI 3.1 document of those routes, and `GET /api/v1/docs` renders that same document as a reference a browser can read and call — the page and the renderer it loads being embedded in the executable, so no internet access is needed —, the footer of both pages linking to it. `target` accepts a canonical key or a label, and a value that names no target is `404`. `from` and `to` accept an RFC 3339 UTC instant or epoch milliseconds inside a fixed calendar domain, `1970-01-01T00:00:00Z` to `2100-01-01T00:00:00Z`, both bounds accepted, `from` inclusive and `to` exclusive; a value outside the domain is `400` naming the parameter, and a `to` in the future is valid, the days that have not begun stating no faults and no down time because unelapsed time is not measured. `limit` is an integer `1`–`1000` defaulting to `100`, and `offset` defaults to `0`. A parameter the route does not accept, a value out of range, and a `from` that is not earlier than `to` are `400` naming the parameter. Every success is an object whose `data` holds an array and whose `meta` states the page, the resolved filters, how many records match them, and the instant the answer was built; an array is never the root of a response. The three data routes write the answer as they read it: `Transfer-Encoding: chunked`, one record per chunk, compressed on the fly when the client accepts gzip, and no `Content-Length`; `/api/v1/faults` reads the history in keyset pages, so the memory of one answer is one page whatever the total. Every failure is an object stating the HTTP status, a stable `code`, the offending `parameter` when there is one, and one fixed message — the detail of a failure, which may name the database path, stays in the log and never in an answer —, the codes being `INVALID_PARAMETER`, `INVALID_RANGE`, `UNKNOWN_TARGET`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `DATABASE_UNAVAILABLE`, and `QUERY_FAILED`. Answers are `application/json; charset=utf-8` with `Cache-Control: no-store`, are gzipped like the page under `--compression auto`, answer `HEAD`, and state `Access-Control-Allow-Origin: *` together with an `OPTIONS` preflight, so a dashboard on another origin reads the same public history. The API never writes and never requires a credential.

- `FR-27`: The `simulate` subcommand serves the same page, the same JSON API and the same export over a history that is generated instead of recorded, so the surface can be exercised, demonstrated and reviewed without a network and without waiting for real days. It runs no probe, reads no event database and writes none, and keeps nothing between requests: `--listen <address:port>` is required, `--history` states how many days of past to present (`30d` by default, `30` accepted, 1 to 3660, anything else refused at startup), and `--seed` (default `0`) selects which history, and `--fault-rate` (default `3`, `0` to `1000`) states how many faults a day a target that fails now and then holds, `0` being a board where nothing goes down. The past is whole UTC days ending today: nothing exists before its first day, the days the page's 360-day selector reaches before it are empty, and nothing exists after now. The history is deterministic — two runs of the same seed show the same faults, with the same causes, durations and latencies, on every platform — and plausible: each target has a life derived from the seed (mostly up, with occasional faults or flapping, scaled by `--fault-rate`), a fault may cross midnight and remains one fault, and every fault states a cause of the code set its method owns and a duration between twenty seconds and forty minutes. The targets are those of the configuration, and a configuration without targets is refused with the same message as `monitor`. `--database` and the `[database]` file key are accepted and ignored, and the Telegram channel is not started. One `INFO` line at startup states the mode, the number of targets, the window, the seed, and that no probe runs and no database is used; the page itself carries no marker.

## Business rules

Rules that always hold, independent of implementation.

- `FR-28`: The `webhook` channel posts one message per event as a JSON document (schema `1`, one line) to an operator-supplied `url`, optionally with `Authorization: Bearer <token>`. A token requires an `https` URL and is read from the file only. A `2xx` answer is success; `429`, `5xx` and a transport failure are retried; a redirect is not followed and any other `4xx` is not retried. The destination is the canonical URL — lower-case scheme and host, the resolved port, the path and the query — and the URL path and the token never appear in a log line or an error, which name `scheme://host[:port]` only.
- `FR-29`: The `logfile` channel appends one line per event to `filename`, whose directory must already exist, and creates the file with mode `0600` on Unix. `logger` (default `notification`) names the logger on the line or in the JSON document; `level` (default `info`) is the most verbose level admitted; `format` is `text` (the diagnostic line) or `jsonl` (one compact JSON document per line, the webhook document plus a `logger` member). `max_bytes` (default `0`; `0` disables rotation, otherwise the accepted range is `1024`–`1073741824`) enables size-based rotation: when appending the next line would take the file past that many bytes, the channel renames `<filename>` to `<filename>.1`, shifts the older rotated files up, deletes what falls past `max_files` (default `5`; accepted range `1`–`100`), and writes the line whole. `max_bytes = 0` keeps the file appended for ever. A rotation that cannot complete logs one `WARN` and the line is still written to the current file, so no event is lost. Rotation happens on a write only, never at start, on a reload, or during the `check` verification of `FR-30`. The channel's own transport failures go to stderr only.
- `FR-30`: The `check` subcommand verifies a configuration without starting the monitor. It reports, in one run and on stdout, one `ok`, `warn`, or `fail` line per check: the target list, every target's interface, the event database (readable, schema not newer than the binary), the effective listen address — the `--listen` override or the file's `listen` key — when one is given, every declared notification channel, and the active snapshot. A `logfile` channel with `max_bytes = 0` is a `warn` under its name: it is legal, but its file grows without a bound. It exits non-zero when any line is `fail`, and zero otherwise. That address is bound and the listener dropped: an address in use is a warning, every other bind failure is a failure. `--probe` performs one real probe per target through the target's method and interface: an `up` verdict is `ok`, a `down` verdict is a warning with its cause, and a local probe failure is a `fail`. `check` starts no worker, sends no notification, writes nothing to the event database, and never prints a secret: the Telegram bot token and the webhook token read `<redacted>`, exactly as `--show-config` prints them. The only write it performs is creating a missing log-file channel's file, exactly as a start would.
- `FR-31`: `monitor --config <main> --try <candidate>` starts with the candidate only when it passes the `check` verification of `FR-30` and its bytes differ from `<main>`. An absent candidate file is a quiet `INFO` no-op: the monitor runs `<main>` and exits zero when stopped, so the flag can stay permanently in a start script or unit file. A candidate that cannot be read, does not parse, does not resolve, or reports a `fail` line logs one `ERROR` naming the reason and one `WARN` stating that `<main>` stays in effect, and the monitor runs `<main>`; a candidate byte-identical to `<main>` is not promoted, produces no backup, and is reported in one `INFO` line. Once every target of the start has completed its first probe without a local failure, the candidate replaces `<main>` atomically, the previous file is kept as `<main>.<UTC timestamp>.bak` in the same directory, and the promotion is logged and announced as one `CONFIG` notification. If the first probe of any target is a local failure, nothing is promoted: the monitor logs one `ERROR` naming the target and the reason and one `WARN` stating that `<main>` is back in effect, notifies the rejection, swaps back to `<main>` in place without a restart, and leaves both files untouched. A failed promotion (an I/O error on the backup or the replace) never stops monitoring and never leaves `<main>` truncated.
- `FR-32`: `<main>.active` holds the exact bytes of the configuration the process started from. It is written once per successful start, after the first probe round of `FR-31` completed with no local failure, created with mode `0600` on Unix, and never read by the monitor itself: it is recovery material, not configuration. A first round that saw a local failure writes nothing, and neither an accepted nor a rejected reload changes it, so it always means "the last configuration that started and probed". Copying it over `<main>` restores that configuration, and the reload applies it within one second without a restart. A start that stops before the first probe names the snapshot and its age; `monitor --fallback-to-active` starts from it when `<main>` cannot be read, parsed, resolved, or pre-flight verified, logging one `WARN` naming the file it used. Without the flag the process fails as it did before. The precedence is candidate, then main, then snapshot; the snapshot is read as configuration only through the same parse, resolve, and `check` pipeline as `<main>`.
- `FR-33`: The `init` subcommand creates a minimal, runnable setup in a new folder. It takes one positional folder and no configuration flag; the folder must not exist or must be empty, and a file or a non-empty folder is refused with a non-zero exit and a message, with nothing written. It writes `uptime-monitor.toml` with the defaults (`interval_ms = 5000`, `timeout_ms = 2000`, `database = "data/events.db"`, `retention_days = 0`), one unprivileged TCP target (`1.1.1.1:443`), a commented ICMP example, and an enabled `logfile` channel `events` at `logs/events.log` with `stabilize_seconds = 0`, `max_bytes = 10485760`, and `max_files = 5`; it creates `data/` and `logs/`; it validates the generated configuration before writing it; it starts no probe, opens no database, binds no socket, reads no configuration, and writes nothing outside the folder; it prints the commands that check and start the setup. The first `check` or start creates `logs/events.log` through the channel, as `FR-29` states. The generated file is an ordinary configuration and no key is new.
- `FR-34`: The `manual` subcommand prints the exact bytes of the user guide embedded at build time to standard output, as Markdown; `man` is a visible alias. It accepts no arguments, reads no configuration, starts no probe, opens no database, binds no socket, creates no file, and spawns no process. When standard output is a terminal it writes one hint to standard error; otherwise standard output is pure Markdown. A closed standard-output pipe is a quiet success; any other write error exits non-zero with a message. The guide is the `docs/USER-GUIDE.md` of the build, so it always matches the binary; there is no renderer, pager, native man page, or new configuration key.
- `FR-35`: The configuration file may state `listen = "ADDRESS:PORT"`. The `monitor` subcommand binds it when `--listen` is absent, `--listen` wins when both are given, and neither means no page (`INV-11`). `--show-config` prints the merged address and `check` verifies it in its `listen` line. `serve` and `simulate` ignore the key and keep their own `--listen` flag, `simulate` still requiring it. A reload that changes the key logs one `WARN` and keeps the bound address until the next start.
- `BR-1`: A target never has two consecutive events with the same state. Rationale: the database models transitions, so a duplicated state is corruption and would also mean a lost transition.
- `BR-2`: A target starts in the `unknown` state. Its first recorded event is the transition out of `unknown`; the event carries `unknown` as the previous state.
- `BR-3`: The effective configuration is always the merge `command line > configuration file > built-in default`, with no hidden environment variable and no implicit third source.
- `BR-4`: A local failure — missing privilege, missing interface, socket error, unwritable database — is never recorded as a target going down. It is reported as an error, and it never changes a target's state. Rationale: the tool must not confuse "I cannot see the network" with "the network is down".
- `BR-5`: A configured interface that does not exist at startup is a fatal configuration error, never a silent fallback to the default interface. Rationale: a silent fallback would measure a different path than the one configured.
- `BR-6`: Timestamps are stored as UTC epoch milliseconds in integer columns; time zone and locale affect presentation only. Rationale: queries and retention stay exact and portable.
- `BR-7`: The current state of a target and its last event are written in the same SQLite transaction, so a reader never observes a state that contradicts the latest event.
- `BR-8`: The database is the integration point for other tools. The tool opens at most one listening socket, the read-only web page and the read-only JSON API of `FR-26`, and only when a listen address is given on the command line or in the configuration file: `serve` never probes, `monitor` probes and serves at the same time. Without a listen address nothing listens, and the outbound traffic is the probes plus the messages of the configured channels: the Bot API for Telegram, the operator's URL for a webhook, and nothing for a log file. Rationale: a page must never be able to alter the history, a monitor that was not asked to serve must not expose a surface, and a monitor without a channel must not reach the network beyond its probes.
- `BR-9`: A database written by a newer schema version than the running binary is reported as an error and left untouched, never migrated downwards.
- `BR-10`: Statistics of the `up` runs are computed from the segments the page draws, and a run that the window opens or closes in the middle of counts as it appears: the first and the last run of a window are lower bounds, never overestimates. Rationale: a figure a reader can check against the bands above it.
- `BR-11`: A relative path written in the configuration file resolves against the directory that holds the file, while a relative path given on the command line resolves against the working directory; an absolute path in either layer is used as written. `.` and `..` are folded lexically and a symlink is not followed. Rationale: a file is a portable unit of configuration, and a service manager that names an absolute `--config` must not need to set the working directory too.

## Non-functional requirements

| Attribute | Target |
|---|---|
| Storage growth | Under 1 MB per 10 000 state transitions; a target that never changes state costs no rows after its first event |
| Probe overhead | One ICMP echo request and one reply per target per interval; no measurable traffic when a target is stable |
| CPU | Below 1 % of one core with 50 targets at a 5 s interval |
| Memory | Resident memory below 20 MB with 100 targets |
| Startup | Configuration parsed and first probe sent within 200 ms |
| Query latency | `query state` returns in under 50 ms on a database with 1 000 000 events |
| Concurrency | Readers never block the writer for more than the WAL checkpoint interval; the writer proceeds with a `busy_timeout` of 5 s |
| Durability | A crash loses at most the event being written; the schema stays consistent |
| Portability | One binary per platform, no runtime dependency, no installer, no shell script in the execution path |
| Footprint | Release binary under 15 MB, container image under 30 MB |
| Reload latency | A change written to the configuration file is detected and applied within 2 s, without losing the last known state |
| Web page | 50 targets over a 24 h window | Rendered in under 300 ms on the NAS; a request never writes to the database |

## Success metrics

- A 30-day run on a QNAP with 20 targets at a 5 s interval produces a database smaller than 1 MB.
- The event count equals the number of observed transitions in an independent audit: no duplicate, no missing transition.
- `query events` returns in under 50 ms while the monitor is running, verified on the deployment device.
- The container image starts on Container Station with only `NET_RAW` added and no privileged mode.
- A contributor reproduces the build and the test suite from a clean checkout by following the developer guide, without asking a question.
- The same binary artifact, built once per platform, runs on macOS, Linux, and Windows without recompilation on the target.

## Assumptions and open questions

### Assumptions

- The implementation language is Rust, chosen in the intake of this baseline; the deployment model is a single statically linked executable.
- SQLite is linked into the binary; no system `libsqlite3` is required on the host.
- The default interval is 5 000 ms and the default timeout is 2 000 ms; both are configurable.
- The first milestone probes IPv4 addresses only. IPv6 is explicitly deferred.
- Retention is disabled by default (`retention_days = 0`), so no event is deleted unless the operator asks for it.
- Probes are privileged: the process needs `root`, `CAP_NET_RAW`, or Administrator on Windows.
- On Windows the interface is given as a numeric interface index; resolving an adapter name is not implemented in this version.
- The QNAP deployment path is Docker through Container Station; a native QPKG is not planned.
- The configuration file is re-read once per second while monitoring runs; a change is applied without a restart, and a changed database path still needs one.
- The notification channels are the three of `FR-25` — Telegram, a webhook, and a log file; everything else consumes the database.
- The tool name and the executable name are both `uptime-monitor`.
- The web page binds `127.0.0.1` by default; exposing it on the LAN (`--listen 0.0.0.0:8642`, or `listen = "0.0.0.0:8642"` in the file) is an explicit operator choice and carries no authentication.

### Open questions

- **IPv6 support** — which interface scoping rules apply to link-local addresses, and is ICMPv6 a separate probe type or the same one? Owner: maintainer.
- **Flap damping** — should a configurable confirmation count (`down` after N consecutive failures) be added, or is one probe per cycle the contract? Owner: maintainer.
- **Alerting hooks** — is a post-transition command hook acceptable as an escape hatch, or does it violate the no-dependency rule? Owner: maintainer. *Resolved:* no hook. The one push channel is the Telegram transport of `FR-25`, chosen over a shell hook and over a webhook because an operator can enable it without exposing a surface or writing a script; every other consumer reads the database ([ADR-0027](./ADR.md)). *Superseded by [ADR-0033](./ADR.md):* a webhook is a built-in channel; a command hook is still out.
- **Multiple addresses per target** — should a label group several addresses, or is one label one address? Owner: maintainer.
- **Web authentication** — is a shared token or HTTP basic authentication worth the complexity for LAN exposure? Owner: maintainer.
