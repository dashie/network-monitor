Reachability monitoring that records incidents, not samples

One executable, no runtime. It probes ICMP, TCP, DNS and HTTP — from the interface you choose — writes a row to SQLite only when a target changes state, and serves that history as a read-only page and a JSON API from the same process.

Why it exists

A small binary, a small history

A ping loop logs every reply; this writes one row when a target goes down and one when it comes back, so storage follows incidents, not probes. The monitor is one stripped Rust executable of about 6 MB, SQLite and the certificate roots inside: no runtime, no sidecar.

Configured in a file, not in a form

No settings screen: the whole configuration is one small TOML file on the server, diffed and versioned like code and restored from a backup with the rest of the machine. Nothing else decides what is probed.

The page is one client of the API

Every figure drawn here is also JSON at /api/v1 — same rows, same order, no key — with an OpenAPI contract and a reference built into the binary. Scripts and dashboards read the board itself: the routes are listed below.

Four checks, one contract

ICMP, TCP, DNS and HTTP sit behind a single Probe trait. A fifth check is a module, a variant and one match arm: the database, the page, the API and the exporter never learn about it.

Read while it writes

The history is SQLite in WAL mode, so query, the page and the API read while the monitor records. No writer lock, no export window, no second database.

One message per incident

Optional notification channels — Telegram, a webhook, a log file — state the transition as it happens, and a recovery only once up has held for the stabilisation window — so a flapping link does not become a stream of alarms.

The four checks

Four kinds of probe answer one question each, and two of them can be told which link to leave from: an icmp or tcp check bound to a named interface behaves as ping -I eth1 does, so on a multi-homed host the record says which link failed and not only that something did.

CheckIt is up when
icmp an echo request to the address is answered before the timeout
tcp a connection to the port is established before the timeout
dns the server answers with a record of the type you asked for, A or AAAA
http the status falls inside the expectation you state, with TLS verified against the roots compiled into the binary

Adding a check touches neither the store, the page, the API nor the exporter: a new Method variant, one module implementing Probe, one arm in the dispatcher. The recipe, and the tests that come with it, are in the developer guide.

How it works

  1. A TOML file declares the targets: method, endpoint, interval, timeout, and optionally an interface, a label and an expectation.
  2. Every cycle asks each target, with its own timeout. A local failure — no privilege, no such interface, a socket error — is logged and changes nothing: the tool never reports "cannot see the network" as "the network is down".
  3. Only a transition is written: the instant, the state reached, and — for a fault — a code and one standard sentence carrying the details of the occurrence.
  4. The page, the JSON API, the gzipped CSV export and query read the same rows. The page needs no account, no framework and no client-side chart library.

The same history as JSON

RouteWhat it states
/api/v1/targets every target: its key, label, interface, state, since when, its last round-trip time, and how long it has been up
/api/v1/faults the faults newest first, each with its target, start, cause, end and duration, and whether it is still open
/api/v1/faults/daily one row per UTC day: the faults, the down time, the mean and the longest up run
/api/v1/openapi.json the OpenAPI 3.1 contract of those routes
/api/v1/docs that contract as a reference a browser can read and call, embedded in the executable: no internet access needed
/export/faults.csv.gz every event as gzipped CSV — the same file import reads back

The API is not a second product beside the page: it is the source of every figure the page draws, from the same rows in the same order, on the same socket. It is read-only, needs no credential and no key, states Access-Control-Allow-Origin: * so a dashboard on another origin can read it, and answers no-store so nothing is cached in front of the history. Every answer is an object with a data array and a meta page, never a bare array, and a failure carries a stable code and names the parameter it refuses.

Quick start

Docker

One container, one volume, and host networking so that interface = "eth1" means the physical interface of the host. NET_RAW is needed for icmp only.

docker run -d --name network-monitor \
  --cap-drop ALL --cap-add NET_RAW --network host \
  -v network-monitor-data:/var/lib/network-monitor \
  -v "$PWD/network-monitor.toml:/etc/network-monitor/config.toml:ro" \
  network-monitor:dev \
  monitor --config /etc/network-monitor/config.toml \
  --listen 0.0.0.0:8642

From source

Rust 1.75 or newer. Raw ICMP sockets need elevated privileges on every platform; tcp, dns and http need none.

cargo build --release
./target/release/network-monitor check --config ./network-monitor.toml
sudo ./target/release/network-monitor monitor --config ./network-monitor.toml \
  --listen 0.0.0.0:8642

Look first, install later

A generated history: no network, no database, and the same seed replays the same board.

./target/release/network-monitor simulate --listen 127.0.0.1:8660 \
  --history 30d --seed 0

The same history is JSON at /api/v1/faults, and the reference at /api/v1/docs opens without a network. The user guide covers every configuration key.

Deliberate limits

  • IPv4 only; no IPv6 targets.
  • HTTP checks do not follow redirects, send no body, and present no credentials or client certificate.
  • DNS asks A and AAAA over UDP on port 53: no DNSSEC, no DNS over TLS or HTTPS.
  • interface is supported on icmp and tcp only.
  • The page has no authentication and no write path, and there is no configuration UI: targets and intervals live in the TOML file on the server, and neither the page nor the API can change them.
  • The trust store is the one compiled into the binary.

Each of these is deliberate rather than missing: one cheap probe, one portable binary, and a page that cannot be used to change anything.

Questions

What exactly does it monitor?

Targets you declare: an address over ICMP, a port over TCP, a DNS record, or an HTTP status that must fall inside an expectation. Each is unknown, up or down, and only a change is recorded.

Do I have to run a database server?

No. The history is one SQLite file next to the binary, in WAL mode, so it can be read while the monitor writes.

What does it cost to run?

One process and one file, with no service beside them to keep alive. What it uses follows the number of targets and the interval you choose; there is no cloud, no account and no subscription.

Is there a hosted version?

No. It runs where the network is — a laptop, a container, an appliance — and is read from there.

Does it send my data anywhere?

Only if you enable a notification channel, which sends one message per incident. The page and the JSON API answer on the address you bind, and serve binds 127.0.0.1 unless you say otherwise.

Does it need root?

Only icmp: raw sockets need root, CAP_NET_RAW or Administrator. tcp, dns and http run unprivileged, so a container started with --cap-drop ALL still monitors without a capability.

Can a script or a dashboard read the history?

Yes — the page is not the only surface. GET /api/v1/targets, GET /api/v1/faults and GET /api/v1/faults/daily answer JSON on the same socket, with Access-Control-Allow-Origin: * and no credential, and /export/faults.csv.gz returns the whole history as CSV. The contract is OpenAPI 3.1 at /api/v1/openapi.json, and the reference at /api/v1/docs works without a network. Nothing on that surface writes.

Can I change the targets from the page?

No, and that is deliberate. The configuration is a TOML file read from the disk — and re-read within a second of a change while monitoring runs — plus the flags of the command line, with the flag winning over the file. It stays a text file you can review, version and back up, next to the database, and no remote surface can add a target, change an interval or alter what is probed.

Can I add my own check?

Yes, and that is what the design is for: one Probe trait, one Method variant, one module. The developer guide gives the steps and the tests that come with them.

Is it free?

Yes. It is released under the MIT licence: use it, change it, ship it, with no account and no fee.
